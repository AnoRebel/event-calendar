---
title: Self-hosting
description: Run the app with Docker, Docker Compose, Dokploy or plain Node, and keep its data safe.
---

The production build is a single Node.js server (`.output/server/index.mjs`) plus a libSQL database. Whatever you run it
on, you need:

1. **`NUXT_APP_SECRET`** — at least 32 random characters (`openssl rand -base64 32`). The server refuses to start in
   production without a strong one.
2. **A database** — the default is a file (`file:/app/.data/events.db` in Docker); point `LIBSQL_URL` at a libSQL
   server or Turso instead if you prefer.
3. **HTTPS** with the original `Host` forwarded, for passkeys.

## Docker Compose (recommended)

```bash
git clone https://github.com/AnoRebel/event-calendar && cd event-calendar
echo "NUXT_APP_SECRET=$(openssl rand -base64 32)" > .env
docker compose up -d
```

The app listens on port 3000 and stores its database in the `calendar-data` volume. Migrations run automatically when
the container starts. To use a separate libSQL server instead of the file:

```bash
LIBSQL_URL=http://sqld:8080 docker compose --profile sqld up -d
```

`bash scripts/deploy.sh` wraps this for repeat deployments: it backs up the database file, builds, starts, waits for
`/api/health`, and rolls back to the previous image if the new one isn't healthy (`bash scripts/deploy.sh rollback` does
it by hand).

## Docker

```bash
docker build -t event-calendar .
docker run -d -p 3000:3000 \
  -e NUXT_APP_SECRET="$(openssl rand -base64 32)" \
  -v calendar-data:/app/.data \
  event-calendar
```

Analytics site ids are read at build time; pass them as build arguments
(`--build-arg NUXT_UMAMI_SITE_ID=…`).

## Dokploy (or another PaaS)

- **Build:** `bun run build` · **Start:** `node .output/server/index.mjs`
- Set the variables from [Configuration](/docs/configuration).
- Either mount a volume and keep the file database, or provision libSQL/Turso and set `LIBSQL_URL` (and
  `LIBSQL_AUTH_TOKEN`).
- Run migrations before the first start and after upgrades: `LIBSQL_URL=… bun run db:migrate` from a checkout, or
  `node scripts/migrate-runtime.mjs` next to the build output.
- Point the health check at `/api/health`.

## Database

| Option | `LIBSQL_URL` |
| --- | --- |
| Local file (default) | `file:./.data/events.db` |
| Self-hosted [sqld](https://github.com/tursodatabase/libsql) | `http://host:8080` |
| [Turso](https://turso.tech) | `libsql://<db>.turso.io` plus `LIBSQL_AUTH_TOKEN` |

Migrations live in `server/db/migrations/` (one folder per migration). Both `bun run db:migrate` (drizzle-kit) and the
container's runtime migrator apply them; the runtime migrator also recognises databases migrated with earlier file
names, so upgrades don't re-run old migrations.

**Backups.** For the file database, copy `events.db` while the app is stopped, or use `scripts/deploy.sh`, which copies
it before each deployment. For sqld or Turso, use their snapshot tools.

## Health

`GET /api/health` runs a real query against the database and returns `503` when it's unreachable:

```bash
curl -f https://calendar.example.com/api/health
```

## Upgrading from earlier versions

- Rename `NUXT_SESSION_PASSWORD` to `NUXT_APP_SECRET`. Everyone is signed out once, because the session cookie
  changed.
- Run the migrations: they add the passkey tables and make passwords optional.
